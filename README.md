# Практика: первый агент на LangGraph

Небольшой проект для первого знакомства с LangGraph. Мы начинаем с уже знакомого
вызова DeepSeek, затем превращаем его в явный цикл:

```text
START -> LLM -> нужен инструмент? -- нет --> END
                 |
                 да
                 v
               tools
                 |
                 +---------------------> LLM
```

В проекте два независимых workflow с одинаковой учебной архитектурой:

- `weather_agent` отвечает на обычные вопросы и получает погоду через Open-Meteo;
- `web_search_agent` отвечает на обычные вопросы и ищет свежие сведения в интернете.

Основной показ проходит в официальном LangSmith Studio: студенты выбирают один из
двух графов, пишут в видимый чат и наблюдают переходы, tool call и `ToolMessage`.
Консольные запуски оставлены для поэтапного объяснения.

Open-Meteo и веб-поиск через `ddgs` не требуют API-ключей. Для ответа модели нужен
`DEEPSEEK_API_KEY`, а для подключения официального Studio — бесплатная учётная
запись и API-ключ LangSmith.

## Что изучаем

- `MessagesState`: состояние графа с историей сообщений;
- LLM-узел: функция читает состояние и добавляет ответ модели;
- `ToolNode`: выполняет выбранный моделью Python-инструмент;
- два отдельных графа и две схемы инструментов: `get_current_weather(city)` и
  `web_search(query)`;
- `tools_condition`: решает, перейти в `tools` или завершить граф;
- ребро `tools -> llm`: возвращает результат инструмента модели;
- `compile()` и `invoke()`: сборка и запуск графа.

Это учебные примеры одного запроса. Собственный frontend, бизнес-база данных и
production-развёртывание намеренно не добавлены; интерфейс даёт LangSmith Studio.

## Установка

Нужен Python 3.11 или новее. Выполняйте команды из папки `week-03-langgraph`.

Linux/macOS:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

Windows PowerShell:

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Откройте `.env` и замените учебную заглушку на ключ:

```dotenv
DEEPSEEK_API_KEY=ваш_ключ
LANGSMITH_API_KEY=ваш_ключ_LangSmith
LANGSMITH_TRACING=false
```

Не публикуйте `.env` и не вставляйте настоящий ключ в исходный код. Проект
использует тот же прямой OpenAI-совместимый адрес DeepSeek, что и предыдущие
материалы: `https://api.deepseek.com`, модель `deepseek-flash`, без повторных
API-запросов при ошибке.

`DEEPSEEK_API_KEY` читается лениво: Agent Server может импортировать и показать
структуру графа без ключа, но первое сообщение в чате потребует действующий ключ.
`LANGSMITH_API_KEY` нужен официальному Studio для подключения к локальному серверу.
При `LANGSMITH_TRACING=false` выполнение остаётся локальным и трассы не отправляются
в LangSmith.

## Основной запуск: чат и граф в Studio

Активируйте окружение, перейдите в корень проекта и запустите:

```bash
langgraph dev
```

Команда читает `langgraph.json`, импортирует оба скомпилированных графа, поднимает
локальный Agent Server без Docker и открывает Studio в браузере. Ожидаемые адреса:

- Agent Server: `http://127.0.0.1:2024`;
- интерактивная документация API: `http://127.0.0.1:2024/docs`;
- Studio: `https://smith.langchain.com/studio/?baseUrl=http://127.0.0.1:2024`.

Если браузер не открылся, скопируйте адрес Studio из терминала. Войдите в
LangSmith и выберите нужный граф:

- `weather_agent` — обычный вопрос или вопрос о текущей погоде;
- `web_search_agent` — обычный вопрос или запрос свежих сведений с источниками.

В режиме **Chat** отправляйте вопросы, а в режиме **Graph** или деталях запуска
покажите узлы `llm` и `tools`, условный переход и состояния сообщений.

Для запуска только сервера, например при проверке, используйте:

```bash
langgraph dev --no-browser
```

Safari блокирует подключение Studio к обычному HTTP на localhost. Для занятия
проще использовать Chrome/Chromium. Официальный запасной вариант:

```bash
langgraph dev --tunnel
```

В Studio нажмите **Connect to a local server**, добавьте выданный HTTPS-адрес в
Allowed Origins и подключитесь к нему. Туннель нужен только из-за ограничений
браузера; сам агент продолжает работать локально.

## Порядок показа на занятии

### 1. Знакомое превращаем в граф — 15 минут

Откройте `src/01_llm_graph.py`. Сначала найдите знакомый вызов `llm.invoke()`,
затем разберите три новых элемента: `MessagesState`, `StateGraph` и рёбра
`START -> llm -> END`.

Запуск:

```bash
python -m src.01_llm_graph
```

Пример вопроса: `Объясни разницу между списком и кортежем в Python.`

### 2. Погодный инструмент и workflow — 25 минут

Откройте `src/weather_tool.py`. Функция сначала ищет город через Geocoding API,
потом передаёт координаты Forecast API и формирует короткое наблюдение. Обсудите,
почему инструмент возвращает факт, а естественный ответ пользователю пишет модель.

Полезные пограничные случаи:

- неизвестный город;
- одноимённые города — нужно добавить регион или страну через запятую;
- таймаут, ошибка HTTP или неожиданный JSON.

Откройте `src/02_weather_graph.py` рядом с первым файлом. Найдите добавленные части:

1. `bind_tools()` сообщает модели схему инструмента;
2. `ToolNode` выполняет выбранную функцию;
3. `tools_condition` проверяет `tool_calls` в последнем сообщении;
4. `tools -> llm` возвращает результат инструмента модели;
5. после второго вызова LLM условие завершает граф.

Покажите экспорт `graph = build_graph()` в конце файла и связь с
`langgraph.json`. Для основной демонстрации запустите Studio:

```bash
langgraph dev
```

Консольный вариант погодного workflow:

```bash
python -m src.02_weather_graph
```

Попробуйте два маршрута в `weather_agent`:

```text
Что такое HTTP?
Какая сейчас погода в Казани?
Какая погода в Springfield?
Какая погода в Springfield, Illinois?
```

В первом запросе инструмент не нужен. Во втором ожидается цикл через `tools`.
Третий должен привести к просьбе уточнить место, а четвёртый — снять
неоднозначность.

### 3. Отдельный workflow веб-поиска — 25 минут

Откройте `src/web_search_tool.py`. Он нормализует запрос, получает до пяти
результатов через бесключевой клиент `ddgs` и возвращает модели заголовок, URL и
короткий фрагмент. Это результаты поиска, а не полное чтение страниц. Модель
обязана показывать ссылки и не должна выполнять инструкции из сниппетов.

Затем откройте `src/03_web_search_graph.py`. Его схема похожа на погодную, но
`ToolNode` знает только `web_search`. В `langgraph.json` этот скомпилированный граф
экспортирован отдельно как `web_search_agent`.

Консольный запуск:

```bash
python -m src.03_web_search_graph
```

В Studio выберите `web_search_agent` и сравните два маршрута:

```text
Что такое HTTP?
Какая сейчас последняя стабильная версия Python? Дай ссылки на источники.
```

Первый вопрос не требует инструмента. Второй должен пройти через `web_search`.

### 4. Сравнение и закрепление — 15 минут

Попросите студентов нарисовать маршрут каждого сообщения и ответить:

- кто выбирает инструмент — Python или модель;
- почему два графа содержат одинаковый цикл, но разные наборы инструментов;
- кто действительно выполняет HTTP-запрос;
- зачем результат инструмента снова отправляется модели;
- что произойдёт, если убрать ребро `tools -> llm`.

Небольшое самостоятельное изменение: добавьте `wind_gusts_10m` в погодный workflow
или параметр давности в поисковый, не смешивая инструменты между графами.

## Как читать состояние после `invoke()`

Для вопроса, которому нужен любой инструмент, список `result["messages"]` обычно
содержит:

1. `HumanMessage` — вопрос пользователя;
2. `AIMessage` с `tool_calls` — выбор модели;
3. `ToolMessage` — результат Python-функции;
4. `AIMessage` — естественный ответ пользователю.

`MessagesState` использует специальный reducer сообщений: узлы возвращают только
новые сообщения, а LangGraph добавляет их к истории.

## Тесты без платного API

Тестам не нужны `DEEPSEEK_API_KEY` и интернет. HTTP-ответы Open-Meteo подменены
через `httpx.MockTransport`, а модель — маленьким тестовым объектом, который
сначала создаёт tool call, а затем читает `ToolMessage`.

```bash
python -m pytest -q
python -m compileall -q src tests
```

Тесты проверяют успешную погоду, ненайденный и неоднозначный город, сетевые/API
ошибки, формат и сбои веб-поиска, изоляцию инструментов между двумя workflow,
полный цикл `LLM -> tools -> LLM`, прямой ответ без инструмента, ленивый импорт
обоих графов и `langgraph.json`. Они не оценивают качество формулировок настоящего
DeepSeek — это проверяется отдельным учебным запуском.

## Частые ошибки

- `DEEPSEEK_API_KEY` не найден: скопируйте `.env.example` в `.env` и вставьте ключ.
- `ModuleNotFoundError`: активируйте `.venv` и повторите установку зависимостей.
- Studio просит войти: войдите в бесплатную учётную запись LangSmith и проверьте
  `LANGSMITH_API_KEY` в `.env`.
- Studio не видит локальный сервер в Safari: используйте Chromium или `--tunnel`.
- Порт 2024 занят: остановите другой процесс или запустите `langgraph dev --port 2025`;
  в последнем случае подключите Studio к `http://127.0.0.1:2025` вручную.
- HTTP 401: проверьте ключ DeepSeek, пробелы и кавычки в `.env`.
- HTTP 402/429: закончился баланс или превышен лимит DeepSeek.
- Погода не найдена: уточните написание, регион или страну.
- Open-Meteo недоступен: инструмент вернёт модели понятное сообщение вместо
  падения программы; повторите позже.
- Веб-поиск ничего не нашёл или временно заблокирован: уточните запрос либо
  повторите позже; отдельного поискового API-ключа в проекте нет.
